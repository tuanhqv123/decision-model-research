# Jev (TypeSafe AI) — "System One" decision model

Status: `done` (all 8 assigned sub-topics covered). This note is evidence for the thesis: build an open "decision model" (TypeSafe's "System One" class) that returns a calibrated, typed decision (choice / score / yes-no) with a probability in ONE forward pass and zero output tokens.

Dates matter. Jev entered public early access **15 September 2026**; the vendor launch post is dated 15 Sep 2026; most independent papers were posted 19–30 Sep 2026. All comparisons below use `jev-1.13.0` unless stated.

---

## 1. The System One / decision-model concept (Kahneman framing)

- **Definition (vendor):** "System One models are a class of AI models built to make fast, structured decisions that software can use directly. A System One model evaluates a state and returns typed answers and probabilities." Jev is "TypeSafe's flagship model and the first System One model." [2]
- **Kahneman framing:** The name is taken from Daniel Kahneman's *Thinking, Fast and Slow* (System 1 = fast, intuitive; System 2 = slow, deliberate), and the model is named after economist **William Stanley Jevons** (the Jevons paradox: cheaper intelligence → more demand). Launch post: "The model class name draws on the distinction between fast, intuitive System 1 thinking and slow, deliberate System 2 reasoning." [1]
- **Interface contract (vendor):** Caller supplies a `state` (text / JSON / array) plus typed `questions`; the model returns typed values + probabilities, **no generated text**. "Think of Jev as a frontier-intelligence function call: unstructured state in, typed probabilistic decisions out." [1][2][4]
- **Where it sits conceptually:** Typed decision models are a repackaging of label-probability classification + constrained decoding + discriminative judging + confidence-based deferral. The **typed readout itself has not shown an independent accuracy advantage** over matched label-probability readouts; the clear gains are in latency and cost. This is the central claim of the first-week evidence audit. [6]

## 2. Architecture: parallel sampler, no autoregressive decoding

- **Sampling (vendor claim):** "Parallel. Generates all outputs in a single query. Incredibly efficient and hardware-aware." vs an LLM which "Generates one token at a time, each conditioned on the last." [1]
- **No text generation:** "While Jev gives up string generation, it's optimized for structured outputs and *can't* hallucinate." [1] "There is no decoding step, so there is no way for it to invent a tool name, fabricate a citation format, or emit malformed JSON." [17]
- **Multiple questions in one pass:** each question is evaluated independently against the same state, in parallel, in a single response — this is what makes a multi-judgment workflow cost one call instead of N. [2][4]
- **Not publicly verifiable.** TypeSafe has **not published the architecture, base model, parameter count, or the sampler design** ("close to the chest for now," per the CEO on Hacker News; no paper as of Sep 2026). The Register's description of RLCD as "a different architecture" is **wrong** — RLCD is a training method, not an architecture. The architecture claim (parallel, non-autoregressive) is externally partly checkable because latency should not scale linearly with question count. [16][5][6]
- **Important acronym collision:** Anthropic published *RLCD: Reinforcement Learning from Contrastive Distillation* (2023) — a **different method**, same three letters. Searching will surface that one first. [16][17]

## 3. RLCD = Reinforcement Learning for Calibrated Decisions (vs RLHF/RLVR)

- **Vendor framing (launch table) [1]:**
  - RLHF: optimizes for human preference — responses raters prefer → chat models; TypeSafe notes it "can also reward sycophancy and confident-sounding hallucinations."
  - RLVR: optimizes for verifiable rewards — outputs a program can check → reasoning models (strong at math, slower/costlier).
  - **RLCD:** optimizes for "calibrated decisions: answers with epistemically honest probabilities on System One tasks" → decision models returning typed values + probabilities.
- **Motivation (vendor):** RLHF preference optimization causes **mode dropping** — the surviving probabilities are shaped by what raters liked, not by how often the answer is right; "if your product *is* the probability, that is fatal." [16]
- **What has NOT been disclosed (as of Sep–Oct 2026):** the reward formulation (whether it is a proper scoring rule — Brier or log loss — used as an RL reward), the base model/parameter count/sampler architecture, the training data, any ablation or RLHF-controlled baseline, and any paper or reliability curve. [16][6] So RLCD is currently a **named goal, not a published method** — externally unverifiable.
- **Open reproductions** that give a concrete recipe (independent, not vendor):
  - **OpenJev-RLCD** [15]: RLCD for a reasoning model — the model samples a rationale, then the answer distribution it commits to is scored with a **strictly proper scoring rule**. A variance identity shows that scoring the mixture of several samples rewards *disagreeing* rationales, and that **RLVR is exactly this mixture objective without its diversity term**. Optimized naively, the per-rationale objective either switches reasoning off or drowns in policy-gradient noise → they use a **two-stage recipe: calibrate, then reinforce**. On Qwen3-1.7B (3 seeds, paired tests) RLCD matches/beats SFT, RFT/STaR and GRPO (each temperature-scaled) in accuracy and **beats all of them in selective prediction**; on GSM8K answer verification, a single query covered ~"TwoCovFive"% of items at ≤5% error vs GRPO's lower coverage. *Note: captions show placeholders (TwoCovFive, GrpoCovFive) — the exact coverage numbers were redacted/placeholders in the fetched abstract.*
  - **eve-rlcd** (anthony-maio) [20]: small open decision model trained with RLCD on Qwen3-0.6B-Base; RLCD differs from the RLVR control by **one subtraction in the reward**, which follows a **Brier-score gradient**.
- **Replicability caveat (independent):** the open reproductions of Jev (e.g., Laya-style) are SFT + temperature-scaling, which the OpenJev-RLCD authors argue is a different route than RLCD. [15][17]

## 4. Typed questions / schema / cardinality (up to 255) and 2-stage scoring

- **Three primitives (vendor docs) [3][4]:**
  - **Choice** — "Which of these options?" → `choice`, `probabilities`, `confidence`. **Up to 255 options.**
  - **Score** — "Which level?" → `score`, `legend`, `probabilities`, `confidence`; **2–10 ordered levels**; `score` can fall between two levels (fractional).
  - **Noul** — "Is this true?" → `noul` ∈ [0,1] (P(yes)); **no separate confidence field**.
- **High cardinality (vendor, launch post):** "Jev supports a cardinality up to 255. For the higher cardinality choices, we do a **2-stage system of scoring independently then making an explicit choice**, hence the occasional slowdown." This is the source for the two-stage high-cardinality behavior the parent flagged. [1]
- **Schema-first / no type errors (vendor):** "Possible outputs and structure are defined in advance. The model never makes type errors. All answers are accompanied with calibrated probabilities and confidence scores." [1][2]
- **Practical guidance:** a Choice "add an `other` or `none of the above` option"; prefer the primitive whose answer your code can act on directly (Choice→code paths, Score→threshold, Noul→`if`). [4]
- **Wikiracing demos** show hundreds-to-thousands of high-cardinality choices and the compounding benefit of not hallucinating — but speedups there are much smaller than the headline because baselines had reasoning off. [1]

## 5. Speed, cost, and the 193.6x / 444.6x workflow claim

- **Pricing (primary docs) [3]:** `jev-1.13.0` = **$42/Btok = $0.042/MTok input; output FREE** ("too cheap to meter"). Rate limits: **100k tokens/s and 80 requests/s** (docs note these adjust dynamically; some aggregators report 250k tok/s / 1200 req/min — a live-dynamic discrepancy, docs.typesafe.ai is authoritative). Context: **64k tokens/request; 32k for `state` + longest question**. Text-only input (no image/audio/video). [3] *(Secondary aggregators report different current limits here, i.e. [Refix]; treat the doc page as the source of truth.)*
- **Latency (vendor claim):** **70–500ms end-to-end**; 40x–200x faster "for the same levels of frontier intelligence" on System One-shaped queries, vs 3–329s for frontier LLMs. TypeSafe notes its evals run from West Coast laptops. [1] The 70–500ms figure is **not in the docs and has no SLA**. [16]
- **Headline workflow claim:** On TypeSafe's four in-house workflow evals, **193.6x faster and 444.6x cheaper**. TypeSafe itself says these "are on the higher end of real world gains," and the workflows were built by its own capabilties team (bias acknowledged). [1][19]
- **Independent, direct measurement (TrueStandard, 18 Sep 2026) [11]:** the multiple is a property of the *comparison*, not the model. Same-day, same route, subtracting round-trip time:
  - One support-ticket classification vs Gemini 3.1 Flash Lite → **1.7x**; vs Claude Haiku 4.5 → **1.9x**; vs Claude Fable 5.1 (thinking) → **5.4x** (Jev server time 477 ms).
  - Six judgments about one ticket: Fable 5.1 thinking, six sequential calls = 74.42 s / $0.16251; same six in **one** Jev call = 0.739 s / $0.00002167 → **100.7x faster, 7,499x cheaper**.
  - Four levers move the multiple: #judgments collapsed into one call, whether the baseline "thinks first," baseline $/token, and whether any output must be written as text.
- **Net evaluation:** vendor's 193.6x/444.6x is **not fabricated but is a self-selected, upper-end comparison** (thinking-mode frontier baselines, multi-step workflows). The defensible range is ~**2x (single call vs cheap model) to ~100x (workflow vs thinking model)**. For a real pipeline that still writes free text, a POC measured **15.9% faster / 30.1% cheaper** on support-ticket triage. [11]

## 6. Calibration and "can't hallucinate" / type-safety guarantees

- **The guarantee, precisely (vendor):** type safety is structural. "A Choice over three options cannot return a fourth... There is no decoding step where a wrong token could slip through." [1] **But TypeSafe's own nuance (launch post):** "Our number is not empirical. Schema matching is guaranteed, thus we can confidently add 0% into the plots." So the **0% hallucination figure is definitional, not measured.** [1][17]
- **What it covers vs does not:** it guarantees **schema validity, not correctness**. The residual risk lives in the "wrong-but-valid" cell — confident, parseable, wrong answers. [17][18] Sun et al. [9] show the model can even **follow the option name, not the definition** bound to it: holding question/state/names/definitions fixed, swapping which definition binds to which name changes decisions; accuracy with original names on >2-option questions was only **56.4%**. So "type-safe is not error-free."
- **Robustness (JevAdvBench) [10]:** on `jev-1.13.0`, **rewording stays within 1.2 percentage points** of the re-run baseline, and **fields outside the schema never reach the model** (type-safety holds against format attacks). **But** appending **one unverified opinion to the state flips 12.1% of decisions** (statistically tied with the strongest injected command, 10.1%) and pushes **38% of confident answers below the 0.8 confidence threshold** that routes to human review. Conclusion: **treat the state as untrusted, argued input.**
- **Calibration — where it holds and where it breaks:**
  - **Holds (independent, reproducible):** DecisionEval [13] ran `jev-1.13.0` on the frozen test split of `LocalLLaMA/typed-decisions` (400 cases / 2,000 decisions, all succeeded, 34 s, $0.0159): **accuracy 0.740** [0.721–0.759], **Brier 0.148** [0.139–0.156], **ECE(10 bins) 0.045** [0.037–0.066]. Confidence routing works: ≥0.7 → 57.6% coverage @ 0.864 acc; ≥0.9 → 24.5% coverage @ 0.937 acc. **Caveat:** the "gold" labels are a teacher-model ensemble distribution, and on **40.6% of decisions the teachers disagreed** — accuracy was 0.841 when they agreed, 0.591 when they didn't. DecisionEval also **could not reproduce** the Laya card's ECE (0.144 vs its 0.045).
  - **Mixed:** Denney & DiGiuseppe (political science) [5] — Jev probabilities better calibrated than GPT-6 Luna's token probabilities on all 8 tasks, **but not consistently better than open-weight Qwen3.8-27B**; and Jev's Choice "confidence" is ~just a rescaling of the chosen option's probability (correlation 0.9997) — adds nothing beyond the probabilities.
  - **Breaks badly on chance/priors (skeptical):** Yu Xi Chau [12] asked Jev repeatedly for the probability of a **fair die / fair coin**; it returned **90.01% for face 1 and 93.23% for heads** (fair refs ≈16.7%/50%). Option-order controls didn't fix it — persistent preference for "1" and "heads." Also found a **hiring anonymity effect** (named-group hire ~93–95% vs no-name 73.79%) and a **small liberal sponsor-label tilt** in bill-sincerity tests. Conclusion: "Its probability field is not evidence of calibration, and its low latency is not evidence that it understands the task better." TypeSafe's public docs do not identify the base model/training corpus, so the bias source is unconfirmable from public info.
  - **Directional community numbers** (single-tester, treat as directional not definitive): calibration "held" on 86 GPQA-diamond physics Qs (87.6% acc) and ~82.5% on duplicate detection; but a legal harness found it **scored answers containing fabricated citations higher than honest ones**, and a SQuAD-checker run agreed with wrong answers at 0.82–1.0 confidence. [17]

## 7. Workflow evals using reference models (GPT-6 Astra, Fable 5.1)

- **Method (vendor):** "We assume there is a correct compute graph (a 'workflow' represented in code) and use the predictions of the largest, smartest, and most expensive external models as reference probabilities... every model gets the same workflow. We test how they compare to the average of the smartest models (in this case, Astra and Fable)." [1][19]
- **Key honesty points (vendor):** (a) they use the **average of GPT-6 Astra and Fable 5.1** as the reference, which "biases answers towards OpenAI and Anthropic's models"; (b) LLMs are run through TypeSafe's own System One adapter wrapper (slowest/costliest way); (c) these are not ground-truth — **agreement with two frontier models, not accuracy vs truth.** [1][19]
- **Vendor-reported result:** Jev ties sonnet 5 at **67.8%** workflow accuracy for **$0.0004 and 0.4 s**, against the averaged Astra/Fable reference; every comparison model scores higher as a workflow than as one prompt. The 67.8% aggregate is reported by community digests of the TypeSafe evals ([rachid-chabane.com radar](https://rachid-chabane.com/en/radar/typesafe-jev-workflow-evals-scored-against-frontier-reference/), which relays TypeSafe's evals site) [1][19].
- **Skeptical framing:** the evidence audit [6] and TrueStandard [11] stress that this benchmark measures **agreement with two reference models, not correctness**; the reference itself is a modeling choice that favors OpenAI/Anthropic. [6][11] (See #8 for independent accuracy measures.)

## 8. Independent / skeptical evaluations — what they conclude

- **Political-science replications (Denney & DiGiuseppe, Leiden) [5]** — most directly on-topic for social-science use: Jev "performs on par with its contemporary commercial and open-weight alternatives when using human coding as a benchmark." **No cost advantage** over GPT-6 Luna at OpenAI batch prices (Jev billed 1.2–3.3x more input tokens per decision, because it counts question + all options as input). "JEV's only obvious advantage is ease of parsing the underlying choice probabilities" and speed. Accuracy/calibration vs humans: better calibrated than Luna's token probs, not consistently better than Qwen3.8-27B.
- **Evidence audit (2609.32160) [6]** reviews 28 first-week papers. Headline: "The first week of evidence supports clear efficiency gains in some workloads, but **not a general accuracy advantage for the typed readout**." Finding on parity: reported "parity" often stands on saturated tests; on discriminating benchmarks hosted Jev trailed stronger hosted models (e.g., **−11.6 median macro-F1** in social-science annotation on Ziems et al.; **−5.8 accuracy** on another). Provides a 14-item evaluation checklist.
- **Rubric judges (2609.29769) [7]:** Jev vs three flash-tier LLM judges over nine panels/seven benchmarks with human judgments. Jev is far cheaper/faster (Jev Choice $0.063; Luna 29x, Gemini 325x, DeepSeek 66x; Jev 29 s vs Luna 859 s, DeepSeek 6,298 s). "Jev can often stand in for them," but **it is wrong in the same places** — a cascade using Jev-as-cheap-judge + LLM fallback only helps where Jev is right alone. Conclusion: Jev's confidence meets the "know when likely wrong" need on most panels, but the LLM fallback was **not wrong somewhere different**, so the cascade didn't beat the fallback.
- **Evaluating & Benchmarking Jev (Univ. Bonn, 2609.37647) [8]** — relatively favorable independent run: high zero-shot accuracy on sentiment/topic/intent/commonsense, **well-calibrated choice probabilities**, confidence supports selective prediction, very low cost; ahead of Qwen3.8-27B on most datasets. **But** it flags an **unexplained MMLU anomal**y: ~96% on calculation-heavy subjects (abstract algebra, college math, college physics 99%) — "hard to reconcile with the vendor's own description" of a single-step non-derivation model; "raises the question of whether MMLU questions were seen during training." Also documents weak spots on HS math 59.6%, advanced math 69.9%, prob/stats 72.9%.
- **Medicine (2609.34024) [14]:** Jev 1.13 ≈ GPT-6 Sol (medium reasoning) on PubMedQA (78.4% vs 78.2%), lower on MetaMedQA (74.8% vs 82.7%), **much lower on DiagnosisArena-MCQ (59.8% vs 82.4%) and NEJM cases (61.8% vs 82.4%)**. Best calibrated on MetaMedQA (ECE 0.063 vs 0.146); answers ≥0.9 prob (52.9% of Qs) were 93.4% accurate, but GPT-6 Sol was as accurate when it accepted a similar share. Poor discrimination on DiagnosisArena (AUROC 0.645 vs 0.768). On 162 "can't answer" questions Jev chose that for 10.5% (vs Sol 8.6%). Median latency 0.27–0.31 s; all 2,823 items cost **$0.08**. "Task-specific validation is required before clinical use."
- **JevAdvBench (2609.31142) [10]:** robustness; see #6 — type-safety immune to format manipulation, but state-injection flips 12.1% of decisions.
- **Fair-coin / bias (yuxichau) [12]:** see #6 — severe miscalibration on chance priors (93% for a fair coin), hiring anonymity effect, small political-sponsor tilt. "Another general-purpose model with model-shaped biases."
- **Type-safety ≠ correctness (Sun et al., 2609.26758) [9]:** see #6 — model follows option name, not bound definition; 56.4% accuracy on >2-option bindings.
- **Aggregated community benchmark table (HITL audit) [17]** — *label each row "who measured what," not a verdict.* Laya's own fine-tuned report: Laya 76.6% vs Jev **72.7%** hard-label; an independent stock-model head-to-head: Jev 92.9% vs Laya 65.3%; a 52-system HF comparison: Jev 74.4% (first); anth.us controlled: Jev 87% vs Laya 80%. Vendor vs independent split cleanly on objective vs subjective tasks. Hard-task accuracy clusters near **72–74%**.

## Findings summary (short)

1. **The concept is a repackaging, not a new intelligence.** "System One" = caller-defined option sets + a single non-autoregressive pass + probabilities intended for direct use. Independent analysis concludes the typed readout gives **no independent accuracy advantage** over matched label-probability classifiers; the real, defensible wins are **latency and cost** [6]. Jev is a frontier-class decision head, not inherently smarter.
2. **Speed/cost margin is real but range-bound.** Vendor's 70–500ms / $0.042-per-MTok-input / free-output is confirmed by third parties [11][13][14]; the **193.6x / 444.6x workflow claim is a self-selected upper end** (thinking-mode frontier baselines, multi-step→one-call batching) that TypeSafe itself flags as "higher end." Independent same-day measurement: **1.7x (single call) to 100.7x (workflow)** [11].
3. **RLCD is a goal, not a published recipe.** TypeSafe has disclosed the name and intent but not the reward, base model, or data [16]. Open reimplementations use a **strictly proper scoring rule** and show **RLVR ≈ RLCD minus a diversity term**, with a two-stage calibrate-then-reinforce recipe that beats SFT/GRPO on accuracy and selective prediction [15][20]. This is the most directly actionable part for building an open model.
4. **"Can't hallucinate" = schema-valid, not correct.** The 0% is definitional (TypeSafe says so [1]); the real failure mode is **confident, parseable, wrong-but-valid** answers, and the model can even follow the option *name* over its bound *definition* (56.4% on >2 options) [9][17][18]. Injection is the sharpest risk: one appended opinion flips 12.1% of decisions and pushes 38% of confident answers below the 0.8-review threshold [10].
5. **Calibration is task-dependent and mostly holds on clean/objective tasks, breaks on priors & subjectivity.** Reproducible ECE ≈ 0.045 on a typed-decisions set with strong confidence-based routing [13]; well-calibrated on MetaMedQA; but a fair coin is reported at **93% heads** [12], and social/legal tasks show group-cue and fabricated-citation distortions [12][17]. The medical replication is the cleanest "it's fast, cheap, and ~frontier on *some* tasks but much worse on complex reasoning" result [14].
