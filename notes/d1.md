## Findings

### 1. Why they are "decision models" (single forward pass, zero output tokens)

- Definition used consistently by Liquid and llama.cpp: a decision model evaluates a situation and returns **calibrated probabilities over a fixed outcome set in one call, with zero generated tokens** — no text, no JSON parsing, no schema validation [1][2][3][15][6].
- Contrast with chat/LLMs: a chat model spends one forward pass per output token and the result still has to be parsed; a decision model reads the input **once** and its answer is always one of the caller's options, with a probability attached [6][15].
- Three question primitives (the "Decision Index schema"): **`noul`** (yes/no → P(yes) in [0,1]); **`choice`** (pick one of named options → probability per option + confidence); **`score`** (position on an ordered 2–10 level rubric → probability-weighted expected level) [1][2][5][6][15].
- The API returns `{"answers": {name: answer}, "usage": {"input_tokens": n, "output_tokens": 0}}` — output_tokens is always 0 [2][3][6].
- Code-level: d1-3B exposes `system_one(state, questions, images=None)` and `system_one_batch([(state, questions[, images])...])`; a state can be text, JSON, or `None` when images are the whole state; the state and its images are read once for all questions [2][14].
- d1-omni-600M adds `probabilities(state, questions, images=None, audio=None)` returning the raw per-option distributions in option order, and supports `images` OR `audio` per request (both → ValueError) [3][14].
- Taxonomy context: TypeSafe calls this model class **"System One"**, and the d1 method/endpoint is literally `system_one()` / `/v1/systemone`. The **Decision Index** benchmark lives in a Jev-branded HF space [17][1][2][3][6][7][15]. d1 is Liquid's open contender against TypeSafe's proprietary **Jev**; Liquid's original blog said d1 was "the first model to rival Jev on text decisions" [5].

### 2. Architecture & training recipe

**d1-3B (3.12B params, text + image)** [1][2][12]
- Architecture: `Lfm2VlForConditionalGeneration` (`model_type: lfm2_vl`); a **decoder-only** LFM backbone with hybrid **short-convolution + full-attention** layers, `tie_word_embeddings=True`.
- Config (from `config.json` [12]): hidden 2048, intermediate 10752, 30 layers, 32 heads, 8 KV heads, `row_theta` 1e6, vocab 128,000, max ctx 32,768. Vision encoder = **SigLIP2 NaFlex shape-optimized 400M** (hidden 1152, 27 layers, 16 heads, patch 16), with a 2048-hidden GELU projector, tiling/thumbnail for large images.
- **Training recipe (vendor-described)** [1]: *"We averaged the weights of LFM2.5-2.6B and the text backbone of LFM2.5-VL-3B to create a better base model. We then fine-tuned checkpoints with different random seeds and data mixtures before merging them again. Training on long inputs, shuffling answer options, and fixing shortcuts in the data made a bigger difference than more advanced techniques."* — i.e. weight averaging [19]+[18], seed/data-merge, long input, option shuffling, shortcut fixes. The vendor states the "practical" data/training choices mattered more than novel methods.
- Not a chat model, does not write text [2].
- Vision retained from base: d1-3B mean **74.1** over 11 public image benchmarks vs base **73.9**; with images removed the same questions score **45.1**, implying the answers come from the images [2].

**d1-omni-600M (587M params, text + image OR audio)** [1][3][13][14]
- Decomposition from model card [3]: **381M shared trunk + decision head, 94M vision encoder, 112M audio encoder**; every modality runs the **same trunk weights**.
- Architecture (`config.json` [13]): text = bidirectional encoder (hidden 1024, 16 layers, 16 heads, 8 KV heads, conv+attention hybrid, vocab 65,536); vision = SigLIP2 (hidden 768, 12 layers, 12 heads); audio = **17-layer FastConformer** (d_model 512, feat_in 128, 8 heads, conv kernel 9); a 2-layer **DecisionHead**; context max 16,384 (image+text cut to 896 tokens; audio+text to 15,360).
- **Training recipe (vendor-described)** [1]: *"We first fine-tuned LFM2.5-Encoder-350M on decision tasks, then added audio and vision in stages. For audio, we trained a FastConformer encoder with an adapter to connect it to the backbone, then fine-tuned the audio encoder with a frozen text backbone. For vision, we took the encoder from LFM2.5-VL-450M and trained an adapter plus LoRA updates to the backbone. Those updates were active only when the input included images, and the vision encoder stayed frozen. We then fine-tuned the full model, merged the LoRA updates, and averaged the weights with the previous checkpoint to regularize the final model."* [20][21]
- Calibration (read from code [14]): **text answers are calibrated with per-type temperatures stored in `config.json`** (keys like `choice:2`, `choice:3-5`, `noul:2`, `score:3-5`, plus default `choice/score/noul` = 1.0); **image and audio answers are the model's softmax as trained**; a `noul` reads the model as `[false, true]` and the code reverses it back to P(yes).
- Precision: trained in float32; on GPU use **float16** (bfloat16 changed the top answer on 0.8% of text rows and 1.7% of audio rows in the vendor's checks). Audio trained only on English speaker↔assistant request turns, clips cut at 30 s [3].

### 3. Benchmarks

**Decision Index v0.2.1 (public split), scored with the official scorer** [1][2][3]:
| Model | Params | Decision Index |
|---|---|---|
| Winnow-12B | 12B | 50.02 |
| **d1-3B** | **3B** | **48.57** |
| Decider 35B-A3B | 36B | 47.11 |
| JPT-9B | 9.7B | 46.89 |
| JPT-4B | 4.7B | 43.04 |
| Decider 4B | 4.7B | 40.70 |
| Decider 2B | 2.3B | 28.97 |
| **d1-omni-600M** | **587M** | **15.95** |

- d1-3B sub-scores: Knowledge 23.8, Language 56.4, Retrieval 52.8, **Tools 74.5**, Arts 36.3. d1-omni-600M: Knowledge 8.3, Language 12.9, Retrieval 35.0, Tools 15.1, Arts 6.8 [2][3].
- **Caveat:** Liquid reports d1-3B 48.57 as "ahead of every 4B and 9B model and on par with Decider 35B-A3B" [1][2], but it is **not** #1 overall — Winnow-12B (50.02) is ahead. So "best under 10B / ~par with Decider 35B-A3B" is accurate; "best overall" is not. **Liquid's rows were self-scored with the official scorer, not submitted to the public leaderboard** — not an independent replication (see §Open questions).

- d1-3B mean **82.9** (highest in table, ahead of Decider 4B 81.1); d1-omni-600M **78.4** (beats Decider 2B 77.1 at ~1/4 the params) [1][3].

**⚠ Two different "means" exist.** The d1-3B model card's own "benchmarks as decisions" table **adds HelpSteer2** (d1-3B 36.7) and then reports d1-3B mean **77.1** (over 8 datasets; Decider 4B 76.2, Decider 2B 71.5) [2]. The 82.9 mean in [1][3] excludes HelpSteer2 (7 datasets). **Do not treat 82.9 and 77.1 as the same measure.** The d1-omni card drops HelpSteer2 because "it may overlap with d1-omni-600M's training data" [3].

**⚠ Number drift between vendor pages.** The HF blog [4] reports slightly different per-dataset values than the Liquid blog/cards [1][2][3] (e.g. d1-3B SQuAD 83.3 vs 85.3; Civil Comments 93.3 vs 93.0; PubMedQA 68.3 vs 66.0; BoolQ 86.3 vs 86.7; XNLI 85.6 vs 85.0; PAWS-X 76.4 vs 76.9). The **means agree (82.9 / 78.4)**. Prefer the Liquid blog + model-card numbers [1][2][3] as the most current; flag the HF-blog variant as a slightly earlier snapshot.

**Additional internal evals** [2][3]: d1-3B 71.8 on DecisionBench (eng v1, all 23,900 rows) and 69.3 on Fast Decisions (dev); d1-omni-600M 76.9 on Fast Decisions (dev).

### 4. Latency (end-to-end, since no output tokens)

d1-3B (vendor-measured, warm calls, one request at a time; columns = one question / 3 questions / 3.4K-token state / 384px image / 64 states packed) [1][2]:
| Device | 1 q | 3 q | 3.4K state | 384px img | 64 states |
|---|---|---|---|---|---|
| Apple M5 Pro (mps) | 30 ms | 41 ms | 640 ms | 62 ms | 78/s |
| Jetson AGX Thor | 16 ms | 20 ms | 220 ms | 35 ms | 262/s |
| Jetson AGX Orin 64GB | 26 ms | 35 ms | 560 ms | 83 ms | 110/s |
| Jetson Orin Nano | 50 ms | 73 ms | 1640 ms | 391 ms (202 ms) | 64/s |
| NVIDIA RTX 4090 (bf16) | 8 ms | 21 ms | 102 ms | 17 ms | 475/s |
| AMD MI325X | 9 ms | 14 ms | 44 ms | 18 ms | 1060/s |

(The Orin Nano 384px cell is reported as 202 ms in [1]; the "64 states" column is throughput in decisions/s for the other rows.) d1-3B answers a **single question in under 50 ms on every measured device**; three questions over one state take ~1.3× one question. On NVIDIA, `model.compile(mode="reduce-overhead")` (CUDA graphs) drops the RTX 4090 single-question latency from **16 ms → 8 ms**; without it a single question is 16 ms, and the first call with a new shape pays for compilation/kernel selection so the vendor advises warming up shapes [2].

**d1-omni-600M has no reported speed numbers** — it is an early research release, "under active development" [1][3].

NVIDIA's **Jetson AI Lab** publishes runnable reproduction examples (JetPack 7.2 / PyTorch 26.09 container) that reproduce the code path and show sample outputs (e.g. `Refund: 0.99`, `Team: billing`, `Urgency: 0.80`) on Jetson, but the latency figures it cites are **Liquid's own** — so these are code-path reproductions, not independent latency measurements [10][11].

### 5. llama.cpp day-one support & NVFP4

- **llama.cpp decision-model endpoint:** `POST /v1/systemone` was added in PR #29818 (merged 2026-10-02), and the API "follows the System One format introduced with TypeSafe's Jev model, so existing clients only need a new base URL" [6][7]. Three question types; state can be a string, JSON, a list of chat messages, or (for vision-capable weights) an image URL.
- **Important nuance:** PR #29818's supported list was **5 models — laya, julia-1, lev, openjev (+vision), kev** — all non-Liquid and mostly BERT/Qwen-based encoders ("decision models are just fancy wrappers around traditional embedding models") [7]. **d1 was not among them.**
- **d1-3B-GGUF repo [8]** ships `d1-3B-BF16.gguf` (5.4 GB), `d1-3B-F16.gguf` (5.4 GB), `d1-3B-Q4_K_M.gguf` (1.67 GB), `d1-3B-Q8_0.gguf` (2.87 GB) plus `mmproj-*-Q8_0/BF16/F16.gguf` for vision, with README instructions to run `llama-server -hf LiquidAI/d1-3B-GGUF:Q8_0` and hit `/v1/systemone` [8]. So Liquid ships day-one llama.cpp artifacts; **I did not independently run it**, and whether the `lfm2_vl` decoder-only arch is wired into the `/v1/systemone` path (which was built around BERT/Qwen encoders) is not confirmed by me — mark as *needs verification*.
- **NVFP4:** Liquid's blog asserts *"Fast from day one — Native support for llama.cpp across Apple, AMD, Qualcomm, and NVIDIA with NVFP4"* [1] — **vendor claim, not independently verified**. In the current `d1-3B-GGUF` repo I found **no NVFP4 .gguf file** (only BF16/F16/Q4_K_M/Q8_0) [8]. NVFP4 is a NVIDIA Blackwell 4-bit float format with general llama.cpp support, but **I could not locate an NVFP4 quant of d1-3B**. Treat as unverified.
- **INT8 path:** `d1-3B-w8a8` is an **INT8 W8A8** quant (torchao `Int8DynamicActivationInt8WeightConfig`, 166 linear LM layers quantized, vision/projector/embeddings/head kept in bf16), 3.8 GB, intended for Jetson/Ampere+ INT8 tensor cores. On Orin 64GB (JetPack 6.2, PyTorch 2.11, torchao 0.18, `compile(mode="reduce-overhead")`), it hits **31 ms** single question vs **37 ms** bf16, and peak memory drops **12.4 GB → 7.9 GB** [9].
- **Runtime requirement:** d1-3B needs `transformers>=5.14` (and `torch`, `torchvision`, `pillow`); d1-omni-600M needs `transformers>=5.15` + `soundfile`. Both load with `trust_remote_code=True` [2][3].

### 6. What the open weights let us reproduce

Open artifacts (all verified present on HF) [2][3][8][9]:
- `LiquidAI/d1-3B`: `model.safetensors` 6.25 GB (bf16), `tokenizer.json`, `config.json`, and ~10 code files (`modeling_d1.py`, `runner.py`, `prompt.py`, `lfm2_vl.py`, `hybrid.py`, `api.py`, `chat_template.jinja`).
- `LiquidAI/d1-omni-600M`: `model.safetensors` 2.35 GB, `config.json`, and code (`modeling_d1.py`, `encoder.py`, `vision.py`, `audio.py`, `prompt.py`).
- `LiquidAI/d1-3B-GGUF` (llama.cpp GGUFs) and `LiquidAI/d1-3B-w8a8` (INT8).

Because the models **ship their own remote code**, you can reproduce the exact, inspectable forward path:
- Single forward pass, zero output tokens; the `system_one` / `system_one_batch` / `probabilities` APIs [2][3][14].
- The three primitives (`noul`/`choice`/`score`) and their answer fields (including `confidence`, `probabilities`, `legend` for score) [2][3][15].
- **Calibration logic** [14]: per-type temperature scaling for text (temperatures in `config.json`), raw softmax for image/audio, and the `noul` `[false,true]`→P(yes) reversal — so you can load d1-omni and replicate both calibrated and raw distributions.
- **Batch packing** (`system_one_batch`, no padding) and the shared-state optimization (state/images/audio read once for all questions) [2][3][14].
- **Precision behavior** (float16 vs bfloat16 tradeoffs, float32 training for omni) [3].
- **Base-model choices** are all downloadable if you want to study/ablate: LFM2.5-VL-3B [18], LFM2.5-2.6B [19], LFM2.5-Encoder-350M [20], LFM2.5-VL-450M [21].

What you **cannot** reproduce from weights alone (inference): the exact training data mixtures, seeds, learning-rate schedules, the "shortcut fixes" and "long-input/option-shuffling" data preprocessing [1], the private vision split of Decision Index v0.3, the proprietary hosted `d1` / TypeSafe `Jev`. The Decision Index 0.2.1 numbers are self-scored; the vision split is private. (Marked as inference.)

**License:** LFM Open License v1.0 — a custom, source-available-style license (not OSI). I read the prelude only; exact commercial-use and attribution terms were not fully verified. The GGUF card also tags `license_name: lfm1.0`. Secondary sources (e.g. localaistats) assert commercial use is permitted, but I did not confirm this from the license text — do not rely on it without reading the full license.
