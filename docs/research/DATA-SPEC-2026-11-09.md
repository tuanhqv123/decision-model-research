# Data specification — AndroidControl rebuild for the decision model

*Written 2026-11-09. Every number here is measured by a script in `scripts/` against the raw corpus,
not carried over from a note. Where a previous note disagrees, this file wins and says why.*

---

## 0. Why this file exists

Three errors were made in this programme while reading this dataset, all of the same class —
**characterising data from a summary instead of the data**:

| # | What was believed | What is true | Cause |
|---|---|---|---|
| 1 | "the corpus is not trajectory data" | `compact_train.jsonl` is 88,288 rows / 13,603 episodes / median **6** steps | read `cur15k`, a **subsampled** derivative (median 1 step) |
| 2 | "the gold element is only in a candidate list 61% of the time" | production `pick_candidates` covers the gold point **99.30%** | applied a hand-written `is_clickable` filter instead of the production one |
| 3 | "155-node classification is the task" | the production candidate list is **median 37** | counted raw a11y nodes, not candidates |

Every figure below names the script that produces it. If a later session disagrees with a number here,
re-run the script; the artifact decides.

**One structural fact to carry forward:** every episode has exactly `n_steps + 1` rows — the extra row is
the synthesised terminal `status`. It is not an annotator action. Episodes are `n_steps` human steps plus

Action distribution over all 89,144 rows:

| action | rows | % |
|---|---|---|
| click | 46,844 | 52.55% |
| **status** | 13,740 | **15.41%** |
| scroll | 9,919 | 11.13% |
| type_text | 5,459 | 6.12% |

| **navigate_home** | **29** | **0.03%** |

`navigate_home` exists in the raw corpus and is **absent from every `compact_*` derivative**. Any rebuild
must keep it, or the action space silently loses an action the runtime can emit.

## 2. Label integrity — `scripts/audit_ac_raw2.py --stage 2`

| Check | Result |
|---|---|
| Rows carrying a target bbox | 52,407 (58.8%) |
| **Target matches a node at IoU > 0.999** | **52,355 / 52,407 = 99.9%** |
| Target matches no node | 52 |
| Inverted / zero-area bbox | 52 |
| Out of bounds | 253 |
| `status` is the **final** row | **13,740 / 13,740 = 100%** |
| `status` appears mid-trajectory | **0** |

**The coordinate labels are trustworthy.** 99.9% of targets are an exact node bbox, so the gold element is
a real object with exact geometry — the task is *select*, not *regress*.

**Consequence for the "is done" question.** Because `status` is always last and never mid-trajectory, the
absent label is free:

```
rows that are NOT status : 74,685   →  implicit is_done = NO
rows that ARE status     : 13,740   →  implicit is_done = YES
```

This is the teaching signal for a `noul("task complete?")` readout. **No new annotation is required.**
The current model has no such slot at all (`grep noul benchmarks/train/ac_common.py` → nothing), which is
the mechanical reason 31 of 104 AndroidWorld episodes declared `status` at median step 7 on tasks needing
8–15.

## 3. The candidate filter — measured, not assumed

`scripts/audit_ac_raw3.py` + a direct cross-check against production `pick_candidates`.

| Filter | candidates/screen (median) | gold point covered |
|---|---|---|
| hand-written `is_clickable` only | 9 | **64.6%** ❌ |
| labelled nodes only | 52 | 95.5% |
| **production `pick_candidates`** (visible ∧ ¬systemui ∧ non-zero bbox ∧ (label ∨ actionable), dedup, smallest first) | **37** | **99.30%** ✅ |

**Use the production function. Do not invent a filter.** The 64.6% figure that once closed this line was
an artifact of a hand-written filter, not a property of the data.

Candidates/screen distribution under the production filter (4 shards, 10,694 spatial rows):
median **37**, mean 42.1, max 216.

## 4. Typing — the question that decided the earlier plan

`type_text` rows: **5,459**. Copyability of the required string against (goal + step_instruction + history):

| | rows | % |
|---|---|---|
| exact substring copyable | **5,279** | **96.7%** |
| copyable after punctuation normalisation | 50 | 0.9% |
| **NOT copyable** | **130** | **2.38%** |

The 130 are genuine composition, e.g.:
`'swimming class started in noida sec 50 in ramagya'`, `'Do you have any dietary restrictions?'`, `'284003'`.

**So pointer-read covers 97.6% of typing, and 2.4% needs generation.**

Current code **drops** the 2.4% (`del g["type_text"]`), so the model never learns "this one I cannot copy".
The fix is not more data — it is a label, see §6.

### What the benchmark actually demands

| Benchmark | tasks needing typing | tasks needing **composed** text |
|---|---|---|
| **AndroidWorld-116** | **19 / 104 scorable (18.3%)**, success **1/19** | **0** — every text is a task parameter in the goal |
| **AndroidLab-138** | ~50 (36%) | **45 query tasks (32.6%)** answer in prose; ~15 need arithmetic |
| AndroidControl (this corpus) | 5,459 rows (6.1%) | **130 rows (2.38%)** |

**This is the load-bearing conclusion for the whole plan:** on AndroidWorld, *no* task requires composing
text. The 19 typing episodes fail not because the model cannot write, but because after a correct
`type_text` it emits **21–23 further clicks**. The defect is state, not generation.

## 5. Action-space coverage

`open_app` rows: 5,089, carrying **697 distinct app names**, of which 353 cover 90% of rows.

| | rows | % |
|---|---|---|
| app name appears in the goal | 4,562 | **89.6%** — pointer-read works |
| app name NOT in the goal | 527 | **10.4%** — requires world knowledge (`"find a flight to Hawaii"` → Booking.com) |

Additionally, **42.2% of step-0 `open_app` rows present a launcher/home screen**, and in **87.2%** of those
the app name is present as a node label under the icon. So that subset is *also* selectable, not guessed.

**Design consequence:** `choice(697)` is not trainable (353 classes are near-singletons). Split it:
- 89.6% → pointer-read from state.
- 42.2% launcher rows → select an icon from ~20 candidates.
- the residue → escalate to a larger model through the existing gate.

### DROP — 311 rows total, 0.35%

| Defect | Rows | Reason |
|---|---|---|
| inverted or zero-area bbox / no matching node | 52 | unscorable label |
| coordinates out of bounds | 253 | label error |

| `type_text` with no target | 20 | label missing |

Also drop: exact-duplicate candidate bboxes (handled inside the filter), and any episode whose

### KEEP — deliberately, with the reason

| Item | Count | Why it stays |
|---|---|---|
| duplicate labels on one screen | 7.3% of spatial rows share the gold's label | real ambiguity; 65% of those are genuinely elsewhere on screen — this is what the **image** is for |

| non-copyable `type_text` | 130 rows | becomes the `escalate` label |

## 7. The training row, exactly

One row = **one decision**, matching the served contract (single image, zero output tokens).

```
image:  the current screenshot, resized to width 720, bicubic, JPEG q90
state:
  Goal: <goal>
  Previous actions:                 # TEXT only, never images
    Step 1: <action_type> <target label>
    ...
  Elements on screen:               # production pick_candidates, cap per §8
    [1] <label|class>(x:..-..% y:..-..%)
    ...
questions (one forward pass):
  action      choice(9)   click|write|long_press|scroll|wait|navigate_back|open_app|terminate|navigate_home
  target_box  box         supervised on click/long_press/type_text
  target_el   choice(K)   the candidate index; supervised when the gold centre is a candidate
  scroll_dir  choice(4)
  app_name    text read   pointer; supervised only when copyable (§5)
  type_text   text read   pointer; supervised only when copyable (§4)
  is_done     noul        NEW — YES on the terminal status row, NO on every other row (§2)
```

### Deliberate omissions

- **No `is_clickable` in the candidate text.** Measured: the rule "pick the clickable node nearest the
  gold" scores **61.9%** without seeing the image, versus the model's 64.7%. Publishing that column would
  hand the answer to the model and make the number meaningless. Keep the column in the artifact for
  *baselines*, never in the input.
- **No screenshots in history.** The backbone has 5/24 sliding-window layers at a 256-token window; a
  multi-image history would be invisible to 18 of 24 layers. Text history is ~15 tokens/step.

### Size budget (measured)

| | tokens |
|---|---|
| goal + history + 37 candidates | **618** median, 2,170 max |
| one 720×1600 image | ~5,800 |
| **per step** | **~6,400** |

Fixed regardless of episode length. 1% of the 256K context, and under the ~64K reliability caveat.

## 8. The cap, and the memory wall that caused a false negative

The previous VA arm trained with `D1_MAX_CANDS=14` because the GPU had 13.9 GB free. That cap discarded
**58.6% of all candidates** — i.e. it removed most of the distractors the contrastive signal comes from.
`benchmarks/results/2026-11-07-loss-redesign-notes.md` already flags this.

With a 37-candidate median, the cap must be **≥40**. Budget: 2,164 tokens at 14 candidates → ~4,000 tokens
at 40, linear. **The trainer's state budget must be checked before the run, not discovered by OOM.**

**Rule:** any result obtained under a cap below the median candidate count is a **lower bound** and must be
labelled as one. A null result under such a cap does not close the line.

## 9. Sampling — and why `cur15k` was wrong

`cur15k` keeps **17% of rows but 66% of episodes**: it took most episodes and kept 1–2 steps of each.
Median 1 step/episode. That is what makes the model a one-click agent.

Rebuild rule — **sample by episode, then keep the whole episode**:

1. Group by `ep`. 2. Shuffle episodes with a fixed seed. 3. Take whole episodes until the row budget is
reached. 4. Never truncate an episode's steps; if the next episode would overflow the budget, skip it and
continue.

This gives a corpus with the same row budget but a **median of 6 steps/episode** instead of 1.

Recommended starting point (all three are defensible; the reason is rows, not episodes):

| Arm | Episodes | Rows | Steps/ep | Note |
|---|---|---|---|---|
| small | ~3,600 | ~24,000 | 6 | fastest signal, matches the "24k no gain" arm's size |
| **medium (recommended)** | ~6,000 | ~39,000 | 6 | half the corpus, keeps episode diversity |
| full | 13,603 | 88,288 | 6 | reference run |

Every arm must hold out the 137 validation episodes **by episode id**, never by row.

## 10. What this spec does NOT claim

- It does not claim the rebuilt corpus will improve AndroidWorld success. At n=116 the MDE is ~14 points
  (`docs/research/A5-parts/Q4-power-analysis.md`), so task success **cannot** certify the change.
- It does not claim pointer-read can compose text. 2.38% cannot, and that is routed to a larger model.
- It does not claim the 7.3% duplicate-label rows are solvable from text. They are solvable only from the
  image, and they cap any text-only ceiling at ~92.7%.

**The measurement that can certify this work** is not task success. It is, on held-out data:
`is_done` accuracy/AUROC, `target_el` accuracy against the production candidate list, and per-step
accuracy on AC-v2 (398 rows) — all of which have far more units than 116 binary outcomes.
