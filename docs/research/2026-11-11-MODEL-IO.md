# What the model reads, outputs and learns: contract v3 (fixed 2026-11-11)

This document describes only what the current code does. The text blocks are **real output** of the code
(`ac_common.element_inputs_v3`, `build_questions`, `gold_answers_v2`). The only edit is that element lists are shortened with "…".
Run card: `docs/research/RUNCARD-v3_s0.md`. Full contract, checked line by line against AndroidWorld: `docs/research/CONTRACT-v3-io.md`.

## 1. What the model reads at each step

1. **The current screenshot.** One image, 720 px wide. AndroidControl training images are stored at 720 px, and at test time the
   1080×2400 AndroidWorld screenshot is downscaled to 720 px.
2. **One block of text (the state)** with five parts:
   - `Goal:` the task instruction.
   - `Progress:` the current step number and how many actions have been taken.
   - `Current app:` the app on screen, inferred from the screen's elements. The keyboard and the system bar are ignored, and the
     launcher is shown as `home screen`.
   - `Previous actions:` one line per earlier action, giving the action, **the element it acted on**, and **whether the screen
     changed**. Only the last 12 actions are listed, preceded by "(n earlier actions not shown)".
   - `Elements on screen:` up to 40 app elements, numbered 1…n in reading order (top to bottom, then left to right).
     **Keyboard keys are excluded.** Each line has the form `id | label | type | state | position (%)`.
3. **A list of apps** to choose from when opening an app. At test time this is the 33 apps the emulator can launch
   (`benchmarks/aw/awenv/aw_apps.json`). In training it is the correct app plus 24 distractor apps.

The model does **not** receive any of the following: screenshots of earlier steps, the task name, the complexity, the step budget,
or anything from the checker.

## 2. What the model outputs at each step (one forward pass, no generated text)

| Question | Kind | Asked when | Meaning |
|---|---|---|---|
| `action` | choose 1 of 9 | always | click, long_press, type_text, scroll, wait, navigate_back, navigate_home, open_app, status (= "done") |
| `target_el` | choose an element number | click, long_press, type_text | which numbered element of the **current** screen's list |
| `app_name` | choose 1 app | open_app | one name from the app list |
| `scroll_dir` | choose 1 of 4 | scroll | up / down / left / right, using AndroidWorld's meaning |
| `type_text` | copy a span | type_text | start and end position of a piece of text that already appears in the input |

**First step** (empty history): the server allows only `open_app` or `status`. Every AndroidWorld task starts on the home screen, and
7 tasks need nothing except declaring done because the device already holds the target state.

### 2.1 What `target_el = 10` means
The model picks **element number 10** in the list it was just given. The code maps that number back to the corresponding element in
AndroidWorld's own element list, takes **the centre of its bounding box**, and taps there. The model never predicts coordinates.
Numbers are only valid on the current screen; the next step numbers the new screen from scratch.

### 2.2 Where typed text comes from
The model **points to a start and an end position** in its input: the text readout scores every position, and the best pair is
chosen. The code then cuts out exactly that span and types it. Example: "Lucas Miller" occupies characters 83–95 of the input, so the
label is `type_text = (83, 95)`. The model learns this from about 1,400 typing steps that have a span label. In 83% of the dataset's
typing steps the text to type appears verbatim in the goal. The model cannot type text that is absent from its input.

## 3. Real examples, start to finish

**First step: AndroidWorld test task "Turn wifi on."** (the emulator's real home screen):
```
Goal: Turn wifi on.
Progress: step 1, 0 actions done
Current app: home screen
Previous actions: none
Elements on screen (id: label | type | state | position):
[1] (no label) | ScrollView | scroll | x:0-100% y:0-100%
[2] Home | View | - | x:0-100% y:5-97%
[4] Gmail | TextView | click,long_click | x:29-48% y:62-73%
… [9] Chrome … [10] VLC … [14] Google app
```
Expected output: `action = open_app`, `app_name = settings`. The harness sends `{"action_type": "open_app", "app_name": "settings"}`
and appends the history line `open_app settings → screen changed`.

**Middle step: training task "Select the hello note & share it with gmail in the note app", step 7:**
```
Goal: Select the hello note & share it with gmail in the note app
Progress: step 7, 6 actions done
Current app: com.google.android.gm
Previous actions:
Step 1: click "hello" → screen changed
Step 2: click "Action" → screen changed
Step 3: click "Send" → screen changed
Step 4: click "Send via other apps" → screen changed
Step 5: click [ImageView] → screen changed
Step 6: type_text "abc@gmail.com" into [EditText] → screen changed
Elements on screen (id: label | type | state | position):
[1] Navigate up | ImageButton | click | x:0-14% y:4-11%
[2] Attach file | Button | click,long_click | x:63-76% y:5-11%
[3] Send | Button | click | x:76-88% y:5-11%
… [11] abc@gmail.com | EditText | click,edit,long_click,focused | x:12-88% y:19-26%
```
Label (the answer the model learns): `action = click`, `target_el = 3` (Send). At test time the harness taps the centre of Send and
the history gains the line `click "Send" → screen changed`.

**Typing step: validation task *write "Lucas Miller" in the drawing on the Sketchbook app*, step 4:** the label is
`action = type_text`, `target_el = 10` (`[10] Text | EditText | click,edit,selected,long_click,focused | x:14-85% y:18-30%`), and
`type_text = (83, 95)` = "Lucas Miller". The harness sends
`{"action_type": "input_text", "x", "y", "text": "Lucas Miller", "clear_text": true}`. AndroidWorld then taps the field, clears the
old text, types the new text and presses Enter.

**Last step:** the label is `action = status`. The harness ends the episode and the AndroidWorld checker reads the device state.

## 4. Training data

| Source | Rows | Notes |
|---|---|---|
| AndroidControl: **every step** of the 4,197 goals that match AndroidWorld task kinds | 27,454 | rebuilt from the raw records; differential check 4,741/4,741 rows identical, 0 mismatches; a screenshot exists for 100% of rows; 0 rows from the test split |
| "Goal → app" rows from AndroidWorld's own task generator | 1,736 | first step on the home screen; 19 task templates held out for evaluation (`heldout_templates.json`) |

Each row is one step plus the history of the earlier steps **of the same goal**. Rows are shuffled during training, which is
standard: what the earlier steps did is already in the history text. Action mix: click 55%, status 14%, open_app 11%, scroll 6%,
type_text 6%, wait 4%, navigate_back 3%.

## 5. One function for training, evaluation and testing

* State text: `ac_common.element_inputs_v3`. The training data, `eval_d1.py` and the server `serving/d1_api.py` all call it.
* History lines: `ac_common.history_entry_with_label` + `effect_changed`. Both the data builder (`add_history_v3.py`) and the live
  agent (`benchmarks/aw/awenv/agent.py: history_entry_v3_for_step`) use them. The test
  `benchmarks/aw/tests/test_agent_history_v3.py` proves the two produce identical strings.
* Element list: the rule `cap40_reading_noime` is stored in the checkpoint, and the server applies exactly that rule.

## 6. Not covered yet (stated up front)

1. **An `answer` action** for the 25 information-retrieval tasks. AndroidControl has no examples of it, so the data would have to come
   from the emulator.
2. **Screenshots of earlier steps.** Deferred until there is a first model to compare against.
3. **Learning from whole-task outcomes or from the model's own mistakes.** In training the history is always the demonstrator's
   correct steps.
4. Icon-only buttons are shown as `[ImageView]`. Their resource id could be added later.
5. The v3 training run **has not started**. The training host's GPU is occupied by another user's job (10.4 GB, since
   14:40 Vietnam time on 2026-11-11).
