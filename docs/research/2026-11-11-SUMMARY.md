## 2. Why R1 reaches only 12–15% (measured) — `docs/research/2026-11-11-DIAGNOSIS-why-low.md`

| # | Cause | Numbers |
|---|---|---|
| 1 | 25 information-retrieval tasks need the `answer` action, which the model does not have | always 0/25 |
| 2 | The app name is copied from the goal; the goal does not name the app → opens `wifi`, `timer`, `''`… | 29–36% of app opens cannot be launched; 24–25 tasks never manage to open an app |
| 3 | The model guesses coordinates from the image; it does not choose an element in the a11y tree | 30–37% of taps land on an element that cannot be tapped |
| 4 | Reports "done" early (often exactly 1 step early) | 21–26 tasks; 103/171 wrong done-reports on `val` come right before the last step |
| 5 | Learns single steps, history is always correct, no examples of correcting a mistake | even given correct history, only 15–17/137 `val` tasks are right at every step; 0/21 tasks with ≥ 9 steps |

## 3. What was agreed

* **One model, imitation learning, no text generation, no external model** (also when creating data).
* **Input at each step:** goal + **1 image of the current screen** (720 px) + history as text + current element list (≤ 40, which keeps 127/130
  of the correct buttons on real AndroidWorld screens) + the device's app list. No task name, complexity or maximum step count is given.
* **Output (a choice, no text generation):** action type (9), element (index number), app (from the list), scroll direction; the text to type is copied from the
  goal (98.4% of the text typed in AndroidControl appears verbatim in the goal).
* **Format matches AndroidWorld:** checked against the original code (`json_action.py`, `actuation.py`, `suite_utils.py`); AndroidControl ↔
  AndroidWorld scroll direction matches (measured on 158 rows); model context 128k tokens, real input ~2,300 tokens. Contract: `docs/research/CONTRACT-v3-io.md`.
* **"Practice tasks of the same type" are allowed** (the same 116 goal templates, different parameters) — the AndroidWorld README/paper permits it and there is no rule against it;
  the 116 test tasks are never used; this is stated openly; 1/3 of the task types are held out from learning to measure ability on new types.
* **The app list** comes from the emulator itself (`pm list packages` ∩ the AndroidWorld names that can be opened) — information about the device, not about the task.
* **The first step may only be "open app" or "report done"** — a fixed rule of the agent, uses no task information; stated openly.
* **Adding the 2 old images: later**, once the first model has a score.
* **Data is only AndroidControl + AndroidWorld.** AMEX (you decided to drop it), AndroidLab (no clean images, real devices with a Chinese UI),
  OS-Atlas (images have the touch-measurement layer printed in, multi-language UI, ~3 elements per screen) were all opened, checked and dropped.

## 5. Mistakes found today and how they were fixed

| Mistake | How it was found | Fix |
|---|---|---|
| The emulator died mid-run; the 10 following tasks were recorded as "scored" | read the per-task results of R1 version 3 | `sweep_infra.py` (+4 tests): move dead tasks to a separate folder and rerun; "infected" tasks are always rerun; save the emulator log |
| The run hung for an hour when the emulator died | the log had no new task for 60+ minutes | `watchdog_runbench.sh` |
| `preflight.py` also counted files that had been removed; `rebuild_index.py` wrote an empty task name | error when rerunning | handled by hand, recorded in the run log |
| "Every AndroidControl task ends with done" | opened the original file: 83,848 actions, 0 `status` | the `status` row was added by our `preprocess_ac.py:126-128`; the record was corrected |
| "AndroidControl has ~22% tasks of the same kind as AndroidWorld", "no Wi-Fi tasks" | counted over all 13,603 train tasks | actually 4,416 tasks (32%), 78 Wi-Fi/Bluetooth/brightness tasks; only AndroidWorld's own apps are absent |
| "117 open-app rows do not name the app" | read row by row | ~75 are only worded differently, ~5 have wrong labels, ~37 really do not name the app |
| Training at 858 px | measured the stored images: 720×1600 | AndroidControl images are stored at 720 px → 858 upsamples blurry images; switched back to 720 |
| The app label for Browser tasks was Chrome | read the goal: "open task.html in the file manager" | changed to `files` |
| Goal generation in a trial run differed from the test tasks | our formula was missing `% 2**32` | the harness is correct; the original formula reproduces each test task exactly |
| Speed-up with 2–4 samples per step | measured: 4 samples + grad-ckpt is slower (2.02 vs 2.36); without grad-ckpt it runs out of memory | training pads the samples to equal length; keep 1 sample per step + grad-ckpt |

## 6. Speed optimisation (d1 documentation + measurements)

* d1 documentation: `system_one_batch` **packs several requests without padding**; `model.compile(mode="reduce-overhead")` runs single queries with
  CUDA graphs (16 → 8 ms on a 4090), and every new shape has to be "warmed up".
* Our training function (`train_d1.forward`) uses `eng._rows` + `attention_mask` → it **pads**; so batching several samples is not faster.
  Training in the unpadded packed style is the real speed-up (estimate, not measured) but needs the sample-assembly part rewritten and a matching test.
* When running the 116 tasks, the time goes mostly to the emulator (task setup, waiting for the screen), not to the model (~0.1 s/step) → compile helps little.
