# Metric tracker before training (2026-11-12)

The operator asked: we must understand whether the problem comes from wrong learning or from something else, and set tracking metrics to be sure the numbers rise.

**Rule:** run no full training, and no AW run, until the candidate (new data that passed a trial of ≤ 300 steps, or a checkpoint) reaches every **blocking** metric below. Each metric is measured by inference on fixed states and takes only a few minutes, so it can be measured beforehand.

## Wrong learning or wrong data?

The model learns **exactly what the data teach**. The data do not teach what we need.

| Error | Evidence | Conclusion |
|---|---|---|
| Repeating after "no change" | Users repeat 3.7% after "no change" and 5.1% after "changed" (`acdata_v4/check.out`). The label does not predict the next action. Label swap: Δ −0.004 (v3), −0.011 (v4). | **The data have no contrast.** This is copycat (Wen et al. 2010.14876): CE has no reason to use the label. 4.4k augmented rows (11%) are too few; VeriGUI 2604.05477 Table 5: 10% error data has almost no effect, 30% does. |
| Stopping early | At the same step position, the AUROC of P(terminate) on validation is 0.94 (v3 and v4). Adding 10 history rows: P(stop) only +0.018. | **Not caused by step position** (the hypothesis of the web report is refuted by the measurement). The model recognises "the screen looks like the final screen of AndroidControl". |
| Stopping early (continued) | Replacing the goal with the goal of another app on the final screen: v3 still stops 28%, v4 25% (`goal_swap.out`). Goal with a second task: v4 0.01 versus v3 0.41. | The model **does** read the goal but does not check it against the screen tightly enough. The data only have "already done" rows at the final step, and no row "the screen looks done but the goal is not done". |
| `answer` | v4 uses `answer` in 7/17 question-answer tasks, correct in 0 tasks. | It was never verified end to end from the model to the checker before training. |
| Overall ceiling | Using only AndroidControl or only offline data, a 3B model reaches 5–13% (AppVLM 11.4 on a set of 82 tasks; VeriGUI 12.6, protocol not stated; GUI-Libra SFT typically 5.2; numbers reported by the papers themselves, **different harness, not directly comparable** with our numbers). Reaching 25% or more needs CoT + offline RL, or rollouts on an emulator. | The realistic target under current constraints is **15–20%**. This must be said plainly. |

## How measured

- **S1, A1:** `benchmarks/results/2026-11-12-v4/actest/compare_actest.py` with the `pred` distribution.
- **S2, S3:** script `probe_swap.sh` on the training machine; summary in `benchmarks/results/2026-11-12-tracker/goal_swap.out`.
- **S4, F1, F2:** `benchmarks/results/2026-11-12-probes2/probe_aw.py` + `summarize.py`, run on the recorded v3h states.
- **F3, W1:** `benchmarks/results/2026-11-12-v3h/aw_compare.py` (prints the protocol and policy of each run, warns when pairing two runs with different policies).
- **C1:** configurations `aw116_v3o_s0_{a,b}` (harness V9).

## Decision order

1. Read C1.
   - If the correct-stop ceiling is ≤ 17%: it is a missing skill, not a stopping error. Stop the stop/loop fix direction and tell the operator.
2. For each fix direction (VeriGUI 30% with paired controls; negative goal-swap right before the final step; copy-text-only for `answer`), run a trial of ≤ 300 steps from v3, measure every blocking metric, and record it in this table.
3. Only a direction that reaches every blocking metric may be trained in full, and only then run AW.
