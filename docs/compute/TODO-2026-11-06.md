| Measurement | Value | Notes |
|---|---|---|
| **Gate A** | **32 passed, 1 skipped, 0 failed** | 4-layer in-process liveness, every emittable action round-trips, `open_app` reaches the app (foreground activity checked), 24/24 canonical apps |
| End-to-end loop | **works** | emulator (host A) + in-process `android_world` + d1-2B served on host B, 12 steps/12 executed |
| Model latency (p50) | **112-119 ms** | matches the published 103-108 ms band; measured *while* the emulator ran on the other box |
| Environment latency (p50) | **1066-1071 ms/step** | the transition pause dominates, as predicted |
| **Invalid-action rate** | **58-75% of emitted actions** | the action-space gap (8 trained types vs 13 AndroidWorld types) — this is the first real result and it is not a grounding finding |
| Crash rate | 1/3 in the first gate run, **false positive** | a single failed probe was treated as death; fixed to require two |

**Mechanism confirmed (19:45):** 24 of 27 `open_app` actions carried `app_name=''`. The API *can* return a
name (probes return `clock`, `Markor` on AC-v2 screenshots), so this is **not** a serving bug — the read
slot goes empty on AndroidWorld screens/out-of-distribution goals, at high confidence (0.92) on the
action slot. The action and name slots disagree; the adapter correctly refuses to invent a name.

**The 58-75% invalid-action rate is the headline of the gate run.** It says the first honest
AndroidWorld number will be dominated by "the model cannot express this action", not by "the model
clicked the wrong thing" — which is exactly what `docs/compute/AW_PROTOCOL.md` demands be reported
separately via `SR_all` vs `SR_reachable`.

## Findings that changed the plan (2026-11-06)

- **The image built and the emulator boots.** `android_world:latest` built with the three runbook patches;
  `aw-emu` is up, `adb devices` shows `emulator-5554 device`, 24 GB cap, host port 5051.
- **The nightly script was broken and nobody knew.** It called `liveness --layers all`, which the probe
  never supported — the "probe failed" I saw first was an argparse error, not a dead device. Fixed in
  `liveness.py` (+2 tests); a filter can no longer be silently ignored.
- **The second 4090 has no `torch`.** It has the data and the checkpoint now, but no Python GPU stack, and
  two unknown processes holding 9.9 GB. Serving d1-2B there means installing a ~2.5 GB stack next to
  someone else's job.
  **Decision: serve the model on the KVM host** (it has working `torch 2.12.1+cu130` in a conda env and
  ~14 GB free VRAM), capped with `D1_MEM_FRAC` so prod services keep their memory. The emulator stays CPU-only.

## Non-negotiable rules for this board

1. **Do not stop a pre-existing container.** Nothing on either 4090 host gets `docker stop` unless it is
   a container this board created; if a safe one-line restore exists it goes in `STOPPED_CONTAINERS.md`
   *and* the user is told before, not after.
2. **Create ⇒ remove.** Everything added (container, image, uploaded file, run dir) is removed at the end.
3. **No number without Gate A + Gate B.** A 116-task run on a broken harness is a retraction, and this
   project already has two.
4. **Long jobs run in background.** Provisioning and any GPU run are launched backgrounded and the work
   continues; nothing polls in a loop.

**What is established:** (1) the harness is correct enough to produce numbers (Gates A and B pass);
(2) the fine-tuned model runs the loop at 109–119 ms/step with zero generated tokens; (3) the app-name read
slot is the dominant online defect and recovering it halves invalid actions; (4) recovering it is **not
sufficient** for task success; (5) the environment crashes on ~1 in 4 episodes, always on the same task, so
no headline benchmark number should be quoted yet.

**What is NOT established:** any task-success claim (n too small, 0 successes), any grounding claim online
(invalid actions never reached a click), any speedup claim (the environment is 10× the model).
