d1-mobile: errors, analysis, what the fixes rest on, targets

Summary dated 2026-11-12. Every number is recomputed from files in the repo, with its denominator. Detailed sources are listed at the bottom of the page.

1. What the model is

d1-mobile is a fine-tune of d1-2B (LiquidAI). It is a decision model: at each step it reads the input in one pass and generates no tokens.

The input of each step consists of:

  • the screen image, 720 px wide;
  • the goal;
  • the history of previous steps, noting whether the screen changed or not;
  • the list of elements on the screen, taken from the accessibility tree.

The output of each step is:

  • one action: click, type, long press, swipe, wait, back, go to the home screen, open app, done, answer;
  • the element that the action targets;
  • the text to type, copied from the text part of the input.

Constraints: only one model, no planner, no external model, trained only on AndroidControl data. No learning from AndroidWorld apps or rollouts, because that would be learning the exam in advance.

The main benchmark is AndroidWorld: 116 tasks, official protocol, seed 30.

Why is the AC-High score high while AndroidWorld is low?
  • AC-High scores per step, and at each step the model is handed the history and the screen of the human demonstrator (teacher forcing). No step checks whether the goal has been reached.
  • If counted per whole task, AC-High is only 22.3%, on par with AndroidWorld (21.7%).
  • The longer the task, the lower it drops: 1 step 59%, 6 steps or more only 9.4%.

3. Error analysis: what it rests on

Reading traces, not guessing. Four independent agents read the traces and screenshots of all 91 failed tasks, one group per agent. For each task, the agent recorded:

  • the first wrong step;
  • what the model did, and what it should have done;
  • evidence: element label, history, image;
  • the AndroidWorld checker logic, read from the upstream code.

In addition there are:

  • an analysis of the model's confidence;
  • an experiment replacing the image with a gray image;
  • a re-reading of the data files and of the other papers against the real files.

Three standout numbers.

  • Stopping at the wrong time. On the AC test no "done" step is correct, yet the model asks to stop on 1,171/8,444 steps. On AndroidWorld there are 49 tasks that declare done before being done.
  • The image matters. Replacing the image with a gray image drops the number of correct steps from 519 to 337/827.
  • Limit of the text-typing mechanism. The d1 code shows that questions of the text/number/date kind can only copy from the text part of the input, and cannot read text in the image.

5. What the constraints block (about 36/91 tasks)

  • Computing dates/times ("next Thursday", "+1 hour"), summing, converting units: a single-pass model has no computation step, and AndroidControl data does not teach this.
  • Finding duplicates across several screens: the model does not remember the content of earlier screens.
  • Typing text that exists only in the image (invoices, expense photos): d1's typing mechanism only copies from the input text part. Using OCR would add an external model.
  • Colours or icons that carry meaning (priority, type of activity): AndroidControl has no labels for them.
  • Clipboard suggestion on the keyboard: the id in AndroidControl is hidden, so there is no data to learn from.

6. Targets and how to check

~28–31 / 115Estimated AndroidWorld for final (24–27%). Reasonable range 22–32. This is not a promise.
< 1,171The number of wrong stop requests on the AC test must fall clearly
≥ 344 / 1,543AC-High: the number of tasks fully correct must not drop
≤ v4 + 0.02P(back | the answer is not back): early-stop threshold at checkpoint 250

Order of checks (set before results exist; if not passed, keep v4 + V13):

  1. Early check at checkpoint 250 on validation.
  2. Gate 1: AC-High, AC-Low, validation.
  3. 13 pre-selected AndroidWorld tasks.
  4. All 116 tasks on the 6 fixed emulators. Report by difficulty, by C1–C4, by number of steps, and compare task by task against v4 + V12.

To go beyond the level of about 30%, the answering part and the never-seen apps must be handled. That needs data from outside AndroidControl, and the constraint would have to be discussed again.

7. What was learned from other papers

PaperMain point, checked against the real files
AndroidControl-Curated / Magma-R1Only the test set is released. The "SR" figure is per step. In the task-improved file, the history also contains the current step's instruction (8,377/8,377 rows). Lesson: quality over quantity, balance by action type.
AMEXHas only per-step scores. The back action is only 0.35%, contrary to the paper's claim. The benefit lies in the screen-understanding data, not in the action sequences.
AndroidGenThe agent generates text and calls the model several times per step. Training data is collected inside AndroidWorld itself, and the retrieval store also comes from scored runs. The "goal prefix" idea is already in the final version.
MobileRLReports by level C1–C4, pass@k and win rate by number of steps. We follow the same format (script aw_report.py). Pass@k is not applicable because our model chooses deterministically.
Unsloth decision modelThe same kind of state/questions/gold data. The lesson "must train enough epochs": final moved from 0.4 epoch to 1 epoch.

8. Running now

The final version (contract v6): 2,322 steps, about 3.5 hours. The early check at checkpoint 250 is running. Gate 1 and AC-Low will run by themselves when training finishes.
