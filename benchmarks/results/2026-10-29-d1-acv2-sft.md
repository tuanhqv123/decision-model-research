Protocol: AC-v2 398 steps (GUI-Libra harness), state = goal + Interaction History (`previous_actions`), Pass@1

non-spatial predictions). Trivial baseline: always-status 21.86%. Leaderboard (self-reported by authors):

## Training data
AndroidControl train split rebuilt from GCS (13,603 eps → 88,288 decisions incl. 13,603 synthesized `status`
rows from final screens; test split and all 350 eval episodes excluded). Curated subsets (`curate_ac.py`):
rule filters (container clicks >20% screen 1,107; instruction says another action 709; dead-zone clicks 134;
typed text not copyable 823) + resampled to the eval action mix → cur5k / cur15k / cur24k.

Findings so far
- After ~4k samples the decision model already beats Qwen3-VL-2B/4B (V track) and Qwen3-VL-8B (VA track).
- **Training on the mixed V+VA format hurts the V track by ~2–4 pts at equal steps (E1 vs E2, E3 vs E2)** → V-only for the headline.
- Error budget (E2@235): click grounding misses 24% of eval, scroll→status/click confusions 9%, status FPs 6%, status misses 4%.
  Small specialist = good Type, weak Grounding (same pattern as Magma-R1/InfiGUI-R1 vs Qwen3-VL-235B on AC-Curated).
- Combining box and element readouts post hoc does not help (best = element 55.53; oracle 59.05).

Round 2 (running): R2a = V-only + procedural memory (k=2 similar TRAIN episodes' step lists, cf. Mem-W);
R2b = V-only on cur24k (more clean data). E2 continues as the V-only baseline.
